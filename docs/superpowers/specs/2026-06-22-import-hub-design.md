# prot-cellar Import Hub Design

**Date:** 2026-06-22
**Status:** Approved (scope: all three importers behind one tracked, UI-triggerable
`ImportRun`; arq worker execution; URL defaults + file upload. Cancellation deferred
to phase 2; targets / scheduled imports out of scope.)

## Goal

Replace the three hand-run CLI importers with a single **standardized, UI-driven,
observable import system**. After this work, an admin opens a new **Import** section
in the app, picks an importer, fills a form (or uploads a file), and submits. The
import runs in a background worker, streams progress back to the UI, and is recorded
as a durable `ImportRun` with a per-record summary and audit trail. The three
existing CLI entrypoints keep working unchanged.

The three importers being standardized:

| `import_type` | Wraps today's | Source | Writes |
|---|---|---|---|
| `PROTEOME` | `scripts/import_proteome.py` | UniProtKB REST (by proteome ID) | organisms, proteomes, proteins, genes, membership |
| `GENE_ENRICHMENT` | `scripts/enrich_genes.py` | Mycobrowser GFF + DeJesus essentiality (URL or uploaded file) | gene location + CONTEXT/VULNERABILITY annotations |
| `GO_ONTOLOGY` | `scripts/import_go_ontology.py` | GO OBO (by URL) | go_terms, go_edges |

## Background / Current State

The **ingestion engine is already well-built and stays as-is.** Each importer is a
runner in `infrastructure/ingestion/` (`import_runner.py:ProteomeImportRunner`,
`gene_enrichment_runner.py:GeneEnrichmentRunner`, `go_import_runner.py:GoImportRunner`)
composed of injectable HTTP clients + pure mappers, delegating to idempotent,
admin-gated application use cases (`BulkUpsertProteins`, `BulkUpsertGenes`,
`BulkEnrichGenes`, GO upsert). All are version-gated and idempotent on
`(source, source_record_id)` + checksum; re-runs are safe and chunk-resumable.

What is **missing**:

- No notion of an **import run** as a tracked, first-class thing — runners `print()`
  to stdout and forget.
- No **API** surface — imports are only reachable via `python -m ...` CLI.
- No **async execution** — runners block for minutes (a proteome streams ~4,000
  entries), which a normal HTTP request cannot.
- No **UI**.

Stack context this design builds on: FastAPI + SQLAlchemy 2.0 async + Postgres,
Lagom DI container built in the app lifespan (`interface/app.py`), Sentinel auth with
workspace-scoped admin roles, domain events feeding an append-only audit trail
(`infrastructure/messaging/`), Valkey (Redis-compatible) already in
`docker-compose.yml` at `localhost:6380` but with **no queue framework**. Frontend is
Next.js 16 / React 19 / Tailwind / shadcn, server state via React Query, client
generated by **Orval** from the OpenAPI spec; nav is data-driven from
`shared/lib/navigation.ts`.

## Architecture

A new `imports` bounded context mirroring the existing
`domain / application / infrastructure / interface` layering. Eight backend units
(§1–8), each one purpose, plus the frontend section (§9).

### 1. `domain/imports/import_run.py` (new) — the aggregate

`ImportRun` aggregate root (GLOBAL reference data, `workspace_id =
GLOBAL_WORKSPACE_ID`, like genes/proteins), carrying:

- `id`, `import_type: ImportType`, `params: dict` (validated per type — see registry),
- `status: ImportStatus` (`QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELLED`),
- `phase: str | None` (free-text stage label, e.g. `"streaming entries"`),
- `progress: Progress(processed: int | None, total: int | None)`,
- `summary: dict` (created/updated/skipped/failed and importer-specific counts),
- `source_version: str | None` (UniProt/GO release, etc.),
- `error: str | None`, `upload_ref: UUID | None`,
- `requested_by: str` (user_id), `created_at/started_at/finished_at`.

State transitions are methods that emit events: `ImportRunQueued`,
`ImportRunStarted`, `ImportRunProgressed`, `ImportRunSucceeded`, `ImportRunFailed`
(`domain/imports/events.py`). Illegal transitions raise `DomainError`. The existing
`AuditEventHandler` captures these automatically — no extra wiring for audit.

`ImportType` and `ImportStatus` are enums in `domain/imports/enums.py`. Progress is
deliberately loose (`processed/total` nullable, `phase` free-text, `summary` a dict)
so all three importers — entry counts, matched/unmatched genes, GO term/edge counts —
fit one shape without a union type.

### 2. `application/imports/registry.py` (new) — the standardization seam

`ImportRegistry` maps `import_type` → an `ImportAdapter` describing:

- `params_model`: a Pydantic model validating that type's params (proteome ID +
  `force/dry_run/limit`; enrichment `tax_id` + `gff_url` + `essentiality` source; GO
  `force`),
- `build_runner(container, reporter) -> Callable[[], Awaitable[RunnerOutcome]]`: wires
  the existing runner from the DI container with a `ProgressReporter` injected, and
  returns a thunk the worker awaits,
- `needs_upload: bool`.

Adding a 4th importer later = register one adapter. No API/UI/worker changes. This is
the "standardize these processes" payoff.

### 3. `application/imports/progress_reporter.py` (new) — the runner→DB sink

`ProgressReporter` protocol: `phase(label)`, `advance(processed, total=None)`,
`set_source_version(v)`, `merge_summary(**counts)`. Two implementations:

- `NoopProgressReporter` (default) — what the CLI scripts get, so they are unchanged.
- `ImportRunProgressReporter` — throttled writer (coalesce updates to ~1/sec or per
  chunk) that loads the `ImportRun`, applies progress, saves through a short UoW.

### 4. Runner refactor (modify, additive) — thread the reporter

`ProteomeImportRunner`, `GeneEnrichmentRunner`, `GoImportRunner` each gain an
**optional** `reporter: ProgressReporter = NoopProgressReporter()` constructor arg and
call it at phase boundaries / per chunk where they currently `print()`. Default no-op
⇒ every existing runner test and CLI script stays green and unchanged. No change to
`(source, source_record_id)` idempotency, chunking, or version gating.

Per-importer progress mapping:
- **Proteome**: `total` = proteome entry count from metadata; `advance` per 500-entry
  chunk; phases `metadata → streaming entries → linking membership`;
  `source_version` = UniProt release.
- **Gene enrichment**: `total` = gene count for the organism; phases
  `fetch GFF → parse → [fetch essentiality] → enrich`; summary
  matched/unmatched/locations_set/annotations_written.
- **GO**: coarse phase progress (`probe version → download → parse → upsert`) +
  final term/edge counts; `source_version` = GO release date.

### 5. `application/imports/` use cases (new)

- `StartImport(command, auth)`: `require_admin(auth)`; validate `params` via the
  registry's `params_model`; reject if a `QUEUED|RUNNING` run already exists for the
  same `(import_type, target_key)` (concurrency guard); persist `ImportRun(QUEUED)`;
  **enqueue** an arq job `run_import(import_run_id)`; return the run id. (Persist +
  enqueue in one UoW commit; the enqueue is the side effect dispatched after commit,
  mirroring the existing commit-then-dispatch pattern.)
- `ListImportRuns(query, auth)` / `GetImportRun(query, auth)`: read models for the UI.
- `CancelImport` — **phase 2**.

### 6. `infrastructure/ingestion/worker.py` (new) — arq worker

arq `WorkerSettings` with:

- `on_startup`: build the **same DI container** the API lifespan builds (engine,
  sessionmaker, UoW, repos, runners), store on `ctx`.
- `run_import(ctx, import_run_id)`: load the run → mark `RUNNING` → resolve adapter
  from the registry → `build_runner(container, ImportRunProgressReporter(run_id))` →
  await it under the synthetic admin/service identity the CLI scripts already use →
  mark `SUCCEEDED` with final summary, or `FAILED` with the captured error. Each
  importer's existing per-chunk transactions are unchanged; the run row is updated in
  its own short UoWs so progress is visible mid-import.

A new `worker` service in `docker-compose.yml` runs
`arq protcellar.infrastructure.ingestion.worker.WorkerSettings` against the existing
Valkey. `arq` added to backend deps; `RedisSettings` read from env (reuse the Valkey
URL already in compose).

### 7. `infrastructure/persistence/.../imports/` (new) — repos + uploads

- `SQLAlchemyImportRunRepository`: `add`, `get`, `list` (newest-first, cursor
  paginated per existing `interface/pagination.py`), `find_active_for(import_type,
  target_key)`.
- `import_uploads` table + repo: stores small uploaded files as a `bytea` row
  (`id`, `filename`, `content_type`, `bytes`, `created_at`). Durable, no shared volume
  between API and worker, no Redis-blob/TTL surprises. The DeJesus table is ~KB; this
  is sufficient. (If we ever need large uploads, swap this repo for object storage —
  the `upload_ref` indirection isolates that change.)

### 8. `interface/routes/imports.py` (new) — API

| Endpoint | Behavior |
|---|---|
| `POST /api/v1/imports` | body `{import_type, params}` → `StartImport` → `202 {id, status}` |
| `GET /api/v1/imports` | `ListImportRuns` → paginated, newest first |
| `GET /api/v1/imports/{id}` | `GetImportRun` → phase, progress, summary, source_version, error, who/when |
| `POST /api/v1/imports/uploads` | multipart → store in `import_uploads` → `{upload_ref}`. Raw **DeJesus XLSX parsed server-side** (folds in `scripts/convert_dejesus_xlsx.py`; `openpyxl` already used there) so the published supplementary file can be dropped directly |
| `POST /api/v1/imports/{id}/cancel` | **phase 2** |

Registered via `include_router` in `interface/app.py`. Use cases exposed through the
DI container exactly like `BulkUpsertProteins` (new `*Dep` aliases in
`interface/dependencies/`). All endpoints admin-gated by the existing Sentinel auth
dependency.

### 9. Frontend — the Import section (new)

- **Nav**: a new `"Data"` group in `shared/lib/navigation.ts` with an **Import** item
  (`/import`, an upload/import icon). Its own group rather than buried under
  Administration, since it is a first-class workflow. `nav-main.tsx` renders it with
  no code change.
- **Feature module** `features/import/` (components / hooks / types / lib / index.ts),
  Orval-regenerated client under `shared/lib/api/imports/`.
- **`/import` page**, two halves:
  - **New import** — pick one of 3 importers (cards), render a **static
    type-specific form** (3 known shapes — clearer than dynamic schema-driven forms):
    - PROTEOME: proteome ID + `force` / `dry-run` / `limit`.
    - GENE_ENRICHMENT: `tax_id`, GFF URL (default prefilled), essentiality as
      **upload-or-URL** (upload → `POST /imports/uploads` → `upload_ref` into params).
    - GO_ONTOLOGY: `force`.
    Submit → `POST /imports`.
  - **Import runs** — table of active + past runs with **live progress bars**
    (React Query `refetchInterval` while any run is `QUEUED|RUNNING`, stops when idle),
    status badges, summary breakdown, source version, who/when, and a **detail
    drawer** showing the error log on failure.

## Data Flow

```
UI new-import form
  └─(optional file)→ POST /imports/uploads ──▶ import_uploads row → {upload_ref}
  └─ POST /imports {type, params(+upload_ref)} ──▶ StartImport (admin)
        persist ImportRun(QUEUED) + enqueue ──▶ Valkey
                                                  │
                          arq worker: run_import(id)
                            registry[type].build_runner(container, reporter=DB sink)
                            existing runner streams source → bulk-upsert use cases
                            reporter writes phase/progress/summary to ImportRun row
                                                  │
   UI Import-runs table ◀── GET /imports (poll while active) ── ImportRun row
```

## Idempotency & Concurrency

- Underlying imports are unchanged: idempotent on `(source, source_record_id)` +
  checksum, version-gated, chunk-resumable. A run cancelled by a deploy/restart is
  simply re-submitted; already-applied chunks are skipped.
- `StartImport` rejects a second `QUEUED|RUNNING` run for the same
  `(import_type, target_key)` (`target_key` = proteome ID / tax_id / `"go"`) to avoid
  two workers fighting over the same data.

## Error Handling

- A per-record `DomainError` stays a `failed` `ItemResult` inside the run's summary
  (existing behavior) — one bad record never aborts the run.
- An unhandled exception in the worker marks the `ImportRun` `FAILED` with the error
  message/stack captured in `error`; the row remains for inspection in the UI.
- Upload of an unparseable essentiality file fails fast at `POST /imports/uploads`
  with a 422 before any run is created.

## Testing

1. **Domain** `tests/unit/domain/test_import_run.py`: state-machine transitions emit
   the right events; illegal transitions raise; progress/summary merge.
2. **Registry/params** `tests/unit/application/test_import_registry.py`: each type's
   `params_model` validates good input and rejects bad (missing proteome ID, unknown
   tax_id shape, etc.).
3. **Runner reporter** extend the three existing runner tests with a fake reporter,
   asserting phase/advance/summary calls — and that the **no-op default** path leaves
   existing assertions unchanged (regression guard).
4. **API** `tests/api/test_imports.py` (real test DB): `StartImport` persists QUEUED +
   enqueues (fake arq); concurrency guard rejects a duplicate active run; list/get
   read models; upload endpoint stores a row and parses a DeJesus XLSX fixture.
5. **Worker** `tests/api/test_import_worker.py`: `run_import` against a stubbed runner
   drives `QUEUED→RUNNING→SUCCEEDED`, writes summary; a raising runner →
   `FAILED` with captured error.
6. Full gates: `make test` (unit + import-linter — the new `imports` context must not
   create illegal cross-context imports), `make test-api`, `make lint` (ruff +
   ruff-format + mypy) all clean. Frontend: `tsc`, `vitest`, `biome` via
   `./node_modules/.bin` (per project convention).

## Decisions / Risks

- **arq over Celery/RQ**: async-native, tiny, fits the FastAPI/asyncio stack and the
  Valkey already present; minimal new surface (one worker service + one dependency).
- **Static per-type forms over dynamic schema-driven forms**: only 3 known importers;
  static forms are clearer and less machinery. A registry-driven param *descriptor*
  endpoint is a future option if importer count grows.
- **Uploads in Postgres `bytea`**: simplest durable option, no API↔worker shared
  volume, no Redis-blob TTL edge cases; fine for KB-scale files. `upload_ref`
  indirection lets us swap to object storage later without touching callers.
- **In-process per-run progress writes**: throttled (~1/sec or per chunk) so progress
  visibility does not turn into a write storm on a 4,000-entry proteome.
- **Cancellation deferred to phase 2**: arq supports job abort; the `CANCELLED` status
  exists in the enum from day one so adding it later is non-breaking.
- **Worker DI duplication**: the worker rebuilds the same container the API lifespan
  builds. Risk of drift — mitigate by extracting the container construction into one
  shared factory both call.

## Phasing

1. `import_runs` + `import_uploads` migrations; `ImportRun` domain + events;
   `ProgressReporter` + no-op refactor of the 3 runners (CLI still works, all gates
   green).
2. arq worker + registry + `StartImport`/list/get use cases + API routes + DI wiring +
   compose `worker` service.
3. Upload endpoint + `import_uploads` repo + server-side XLSX parse.
4. Frontend Import section (nav, forms, live runs table, detail drawer) + Orval regen.
5. *(optional)* cancellation; registry-driven dynamic param descriptors.

## Final Step (the actual ask)

After all gates are green and the worker is up (`make up` brings Postgres + Valkey +
worker): open the app → **Import** → run a proteome import (e.g. `UP000001584`),
watch live progress, then run gene enrichment with an uploaded DeJesus table and a GO
ontology import — all from the UI, each recorded as an `ImportRun` with a summary and
audit trail.
